# CI Grants Guard Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the privilege assertions that protect PRs #46, #50, #52 and #54 run automatically on every PR, so a migration that over-grants a table fails the build instead of waiting for someone to run a SQL file by hand.

**Architecture:** A new hermetic SQL file holds eight pure-catalog checks and raises an exception when any verdict is not `PASS`. A second CI job starts the Supabase CLI's local stack, applies all migrations, and runs that file through `psql -v ON_ERROR_STOP=1`. The two-account behavioural harness keeps everything that needs real users.

**Tech Stack:** PostgreSQL 17 (Supabase), Supabase CLI (already a devDependency at `^2.113.0`), GitHub Actions, `psql`.

## Global Constraints

- End every commit message with: `Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`
- **The new file must be hermetic.** No `set role`, no `auth.uid()`, no reference to `auth.users`, no `REPLACE_WITH_` placeholder, no dependency on any row existing. It must produce identical verdicts on an empty freshly migrated database and on the live project.
- **The new file must be read-only.** Only `create temp table`, `insert into` that temp table, `select`, and the final `raise`. It must never write to a `public` table, so it is safe to run against the live project.
- **Verdict vocabulary is unchanged:** `PASS`, `FAIL — <reason>`, `VACUOUS — <reason>`, `SKIP — <reason>`. In the hermetic file only `PASS` is acceptable; the other three fail the build.
- **Do NOT edit any file in `supabase/migrations/` that already exists.** Those have been applied; changing their text would make the repo diverge from what ran.
- **Do NOT add a dependency.** The Supabase CLI is already in `devDependencies`.
- Never commit a real email address. The two `REPLACE_WITH_` placeholders in `rls-assertions.sql` stay exactly as they are.

- [ ] **Step 1: Create the file with its header and results table**

Create `docs/verification/grants-assertions.sql`:

```sql
-- ============================================================================
-- Orbit Flo — privilege assertions (hermetic)
--
-- WHAT THIS FILE IS
--   Eight checks that read only the system catalogs. No accounts, no seed
--   data, no SET ROLE, no writes. It produces identical verdicts against an
--   empty freshly migrated database and against the live project, which is
--   what lets CI run it on every pull request.
--
--   This is the guard for four merged fixes:
--     #46  anon could execute security-definer functions
--     #50  anon held table privileges on 33 tables in public
--     #52  the viewer role existed and could be assigned
--     #54  authenticated could rewrite identity and provenance columns
--
-- WHY IT HAS TO BE AUTOMATIC
--   Supabase's platform default privileges are owned by supabase_admin and
--   cannot be altered by postgres. They grant ALL on every newly created
--   public table to anon and authenticated. A migration that creates a table
--   is over-granted the instant it runs and nothing in the database objects.
--   Ending every table-creating migration with a revoke is a habit; this file
--   is what notices when the habit lapses.
--
-- HOW TO RUN
--   In CI, and locally against a throwaway database:
--     psql "$DB_URL" -v ON_ERROR_STOP=1 -f docs/verification/grants-assertions.sql
--
--   Against the live project (safe — this file never writes):
--     npx supabase db query --linked -f docs/verification/grants-assertions.sql
--
-- HOW IT REPORTS
--   It prints one row per check, failures first, then raises an exception if
--   any verdict is not PASS or if fewer checks ran than expected. The exit
--   code lives in the SQL rather than in a wrapper so that both invocations
--   above fail loudly instead of printing a table you have to read carefully.
--
--   PASS            the privilege boundary is where it should be
--   FAIL — …        it is not
--   VACUOUS — …     the check ran but proved nothing
--   SKIP — …        preconditions absent
--
--   In THIS file, only PASS is acceptable. There are no preconditions that can
--   legitimately be absent, so VACUOUS and SKIP fail the build exactly as FAIL
--   does. The vocabulary is kept anyway so a check that degrades says why,
--   rather than reporting a failure for the wrong reason.
--
-- WHAT THIS FILE DOES NOT COVER
--   Row-level security. Every policy, every isolation boundary, and every
--   trigger side effect needs two signed-in accounts and real data; those live
--   in docs/verification/rls-assertions.sql and are still run by hand. Running
--   this file green does NOT mean the RLS boundaries were verified.
-- ============================================================================

create temp table grant_results (
  check_group text,
  subject     text,
  expected    text,
  actual      text,
  verdict     text
);
```

- [ ] **Step 2: Add the anon checks and the function checks**

Append to the same file. This is checks 1–4, moved verbatim from `rls-assertions.sql` with `rls_results` renamed to `grant_results`:

```sql
-- ---------------------------------------------------------------------------
-- 1-2. ANON HOLDS NOTHING (#50), and the revoke did not overreach.
-- ---------------------------------------------------------------------------

do $$
declare
  leaked   text;
  n_leaked integer;
  total    integer;
  readable integer;
begin
  select
    string_agg(c.relname, ', ' order by c.relname),
    count(*)
  into leaked, n_leaked
  from pg_class c
  join pg_namespace n on n.oid = c.relnamespace
  where n.nspname = 'public'
    and c.relkind = 'r'
    and (
      has_table_privilege('anon', c.oid, 'SELECT')
      or has_table_privilege('anon', c.oid, 'INSERT')
      or has_table_privilege('anon', c.oid, 'UPDATE')
      or has_table_privilege('anon', c.oid, 'DELETE')
    );

  insert into grant_results
  values (
    'grants',
    'anon holds no privilege on any public table',
    '0 tables',
    coalesce(n_leaked, 0) || ' tables' || coalesce(': ' || leaked, ''),
    case when coalesce(n_leaked, 0) = 0 then 'PASS'
         else 'FAIL — revoke anon on these, they arrived pre-granted' end
  );

  -- The opposite error. A revoke that overreached would break every signed-in
  -- request, and would otherwise look identical to a clean pass above.
  select
    count(*),
    count(*) filter (where has_table_privilege('authenticated', c.oid, 'SELECT'))
  into total, readable
  from pg_class c
  join pg_namespace n on n.oid = c.relnamespace
  where n.nspname = 'public' and c.relkind = 'r';

  insert into grant_results
  values (
    'grants',
    'authenticated can still read every public table',
    total || ' tables',
    readable || ' tables',
    case when readable = total then 'PASS' else 'FAIL — the revoke overreached' end
  );
end
$$;


-- ---------------------------------------------------------------------------
-- 3-4. SECURITY-DEFINER FUNCTIONS ARE NOT ANON-CALLABLE (#46).
--
--      A security definer function bypasses RLS entirely, so for it the grant
--      IS the boundary. preview_workspace_invitation is the one deliberate
--      exception: /invite/:token renders before sign-in.
-- ---------------------------------------------------------------------------

do $$
declare
  exposed text;
begin
  select string_agg(p.proname, ', ' order by p.proname)
  into exposed
  from pg_proc p
  join pg_namespace n on n.oid = p.pronamespace
  where n.nspname = 'public'
    and p.prosecdef
    and has_function_privilege('anon', p.oid, 'EXECUTE')
    and p.proname <> 'preview_workspace_invitation';

  insert into grant_results
  values (
    'grants',
    'no security-definer function is anon-callable',
    'none but preview_workspace_invitation',
    coalesce(exposed, 'none'),
    case when exposed is null then 'PASS' else 'FAIL — revoke anon on these' end
  );

  insert into grant_results
  values (
    'grants',
    'preview_workspace_invitation stays anon-callable',
    'true',
    has_function_privilege('anon', 'public.preview_workspace_invitation(text)', 'EXECUTE')::text,
    case when has_function_privilege('anon', 'public.preview_workspace_invitation(text)', 'EXECUTE')
         then 'PASS'
         else 'FAIL — the invite page will break for signed-out recipients' end
  );
end
$$;
```

- [ ] **Step 3: Add the new viewer check**

This one is NOT moved — it replaces `nobody holds the viewer role`, which counts rows and so would report `PASS` on an empty database while proving nothing. Append:

```sql
-- ---------------------------------------------------------------------------
-- 5. VIEWER IS UNREACHABLE (#52).
--
--    202608200002_role_model.sql added a CHECK on both workspace_members.role
--    and workspace_invitations.role forbidding 'viewer'. The enum VALUE stays,
--    because dropping one means recreating the type and every policy and
--    function depending on it.
--
--    HONEST SCOPE: this proves the constraints are ATTACHED AND VALIDATED, not
--    that they reject. Proving refusal needs an insert probe, which needs a
--    real workspace row, which is not hermetic — that probe lives in
--    rls-assertions.sql and is still run by hand. What this catches is a
--    migration dropping or invalidating the constraint, which is the drift
--    that would actually happen.
--
--    The row-count version ('nobody holds the viewer role') stays in
--    rls-assertions.sql, where there is real data to count.
-- ---------------------------------------------------------------------------

do $$
declare
  found_valid integer;
begin
  select count(*)
  into found_valid
  from pg_constraint
  where conname in (
      'workspace_members_role_not_viewer',
      'workspace_invitations_role_not_viewer'
    )
    and contype = 'c'
    and convalidated;

  insert into grant_results
  values (
    'grants',
    'both role columns refuse viewer by constraint',
    '2 validated CHECK constraints',
    found_valid || ' validated CHECK constraints',
    case when found_valid = 2 then 'PASS'
         else 'FAIL — a role CHECK is missing, dropped, or NOT VALID; viewer is assignable again' end
  );
end
$$;
```

- [ ] **Step 4: Add the column-grant checks**

Checks 6–8, moved verbatim. Append:

```sql
-- ---------------------------------------------------------------------------
-- 6-8. AUTHENTICATED CANNOT REWRITE IDENTITY OR PROVENANCE (#54), plus the two
--      inverse checks that make a green result mean something.
--
--      Checks 7 and 8 are not redundant with each other. Check 7 counts
--      COLUMNS and would still read clean if one table were wholly broken
--      among 33 healthy ones; check 8 counts TABLES so a single wounded table
--      cannot hide. public.signals is excluded from check 7 by name: it
--      legitimately exposes only read_at.
--
--      All three cover partitioned tables (relkind in ('r','p')), because a
--      partitioned table would otherwise arrive with platform-default
--      table-wide UPDATE and go unseen by relkind = 'r' alone.
-- ---------------------------------------------------------------------------

do $$
declare
  writable        text;
  n_writable      integer;
  not_writable    text;
  n_not_writable  integer;
  starved_tables  text;
  n_starved       integer;
begin
  select
    string_agg(c.table_name || '.' || c.column_name, ', ' order by c.table_name, c.column_name),
    count(*)
  into writable, n_writable
  from information_schema.columns c
  join pg_class pc on pc.relname = c.table_name
  join pg_namespace n on n.oid = pc.relnamespace and n.nspname = 'public'
  where c.table_schema = 'public'
    and pc.relkind in ('r', 'p')
    and c.column_name in ('id', 'workspace_id', 'created_by', 'created_at', 'updated_at')
    and has_column_privilege('authenticated', ('public.' || quote_ident(c.table_name))::regclass, c.column_name, 'UPDATE');

  insert into grant_results
  values (
    'grants',
    'authenticated cannot rewrite identity or provenance columns',
    '0 columns',
    coalesce(n_writable, 0) || ' columns' || coalesce(': ' || writable, ''),
    case when coalesce(n_writable, 0) = 0 then 'PASS'
         else 'FAIL — revoke update on these; a new table arrives pre-granted' end
  );

  select
    string_agg(c.table_name || '.' || c.column_name, ', ' order by c.table_name, c.column_name),
    count(*)
  into not_writable, n_not_writable
  from information_schema.columns c
  join pg_class pc on pc.relname = c.table_name
  join pg_namespace n on n.oid = pc.relnamespace and n.nspname = 'public'
  where c.table_schema = 'public'
    and pc.relkind in ('r', 'p')
    and pc.relname <> 'signals'
    and c.column_name not in ('id', 'workspace_id', 'created_by', 'created_at', 'updated_at')
    and not has_column_privilege('authenticated', ('public.' || quote_ident(c.table_name))::regclass, c.column_name, 'UPDATE');

  insert into grant_results
  values (
    'grants',
    'authenticated can edit every non-protected column',
    '0 columns',
    coalesce(n_not_writable, 0) || ' columns' || coalesce(': ' || not_writable, ''),
    case when coalesce(n_not_writable, 0) = 0 then 'PASS'
         else 'FAIL — these columns cannot be edited; a column added later inherits no grant' end
  );

  select
    string_agg(pc.relname, ', ' order by pc.relname),
    count(*)
  into starved_tables, n_starved
  from pg_class pc
  join pg_namespace n on n.oid = pc.relnamespace and n.nspname = 'public'
  where pc.relkind in ('r', 'p')
    and not exists (
      select 1
      from information_schema.columns c
      where c.table_schema = 'public'
        and c.table_name = pc.relname
        and has_column_privilege('authenticated', ('public.' || quote_ident(c.table_name))::regclass, c.column_name, 'UPDATE')
    );

  insert into grant_results
  values (
    'grants',
    'every table still has some updatable column',
    '0 tables',
    coalesce(n_starved, 0) || ' tables' || coalesce(': ' || starved_tables, ''),
    case when coalesce(n_starved, 0) = 0 then 'PASS'
         else 'FAIL — these tables cannot be edited at all: ' || coalesce(starved_tables, '') end
  );
end
$$;
```

- [ ] **Step 5: Add the report and the exit code**

Append. The `select` runs first so its output reaches the log before the raise aborts:

```sql
-- ---------------------------------------------------------------------------
-- Report. Failures first, so a CI log shows the problem without scrolling.
-- ---------------------------------------------------------------------------

select
  subject,
  expected,
  actual,
  verdict
from grant_results
order by
  case
    when verdict like 'FAIL%'    then 0
    when verdict like 'VACUOUS%' then 1
    when verdict like 'SKIP%'    then 2
    else 3
  end,
  subject;


-- ---------------------------------------------------------------------------
-- Exit code. Raising here rather than in a wrapper means every way of running
-- this file fails loudly — psql -v ON_ERROR_STOP=1 exits non-zero, and a human
-- running it through `supabase db query` gets an error instead of a table they
-- have to read carefully.
--
-- The count floor is the file-level version of the trap this whole harness
-- exists to avoid: a script that silently executed nothing would otherwise
-- report a clean zero failures. It is a FLOOR, not an equality, so adding a
-- ninth check needs no edit here — but deleting one fails the build.
-- ---------------------------------------------------------------------------

do $$
declare
  expected_checks constant integer := 8;
  n_total   integer;
  n_bad     integer;
  bad_list  text;
begin
  select count(*) into n_total from grant_results;

  if n_total < expected_checks then
    raise exception
      'grants-assertions ran % checks, expected at least % — the script did not execute in full',
      n_total, expected_checks;
  end if;

  select count(*), string_agg(subject || ' → ' || verdict, '; ' order by subject)
  into n_bad, bad_list
  from grant_results
  where verdict not like 'PASS%';

  if n_bad > 0 then
    raise exception 'grants-assertions: % of % checks did not pass — %',
      n_bad, n_total, bad_list;
  end if;

  raise notice 'grants-assertions: all % checks passed', n_total;
end
$$;
```

## Task 3: The red-proof

**Files:**
- Create then delete: `supabase/migrations/202612310001_scratch_redproof.sql`

**Interfaces:**
- Consumes: the `guards` job from Task 2.

### Why this task exists

The entire design rests on one unverified premise: **that the Supabase CLI's local stack reproduces the hosted platform's default privileges** — the mechanism that silently grants `anon` everything on a newly created table. If it does not, the guard passes forever while proving nothing, which is worse than no guard because it looks like coverage.

The only way to settle it is to create a table and watch the guard go red.

This project has already shipped one privilege statement that was a global no-op (PR #54) and it was an end-state assertion, not reasoning, that caught it. Reasoning about Postgres grant mechanics has been wrong four times in this codebase's history. Measure it.

## Task 4: Trim the two-account harness

**Files:**
- Modify: `docs/verification/rls-assertions.sql`

**Interfaces:**
- Consumes: `docs/verification/grants-assertions.sql` from Task 1, which now owns the moved checks.

### Background you need

`rls-assertions.sql` is 1616 lines. Its `grants` group holds 13 named checks. Seven moved to the hermetic file in Task 1 and must now be deleted here, so each check exists in exactly one file and the two cannot drift.

**Five checks stay**, because each needs a workspace, a project, or fixtures it builds itself:

- `nobody holds the viewer role` — a row count, meaningful here where there is data
- `the database refuses a viewer invitation` — an insert probe needing a workspace
- `an owner's membership can be deleted when another owner remains`

## Self-review notes

**Spec coverage.** The eight hermetic checks and the exit code → Task 1. `supabase/config.toml` and the parallel `guards` job → Task 2. The red-proof, which the spec names as the gating validation → Task 3. The split of `rls-assertions.sql`, the relabelling, and both file headers → Tasks 1 and 4. The spec's "only PASS is acceptable" rule and the count floor → Task 1 Step 5. The spec's "no GitHub secrets, never contacts the linked project" requirement → Task 2 Step 3 uses only the fixed local URL.

**Why Task 1 verifies against the live project.** The hermetic file is read-only by construction, so running it against the linked project costs nothing and proves the checks work against a real Supabase schema before any CI plumbing exists. It also means a genuine privilege regression on the live database would be caught in Task 1 rather than blamed on the new CI job in Task 3.

**Why the red-proof is its own task and not a step.** It can fail in a way that invalidates the spec's central claim, and that outcome needs a reviewer's gate rather than being buried in a step of a larger task. Its instructions say explicitly not to force a failure, because the tempting response to a green red-proof is to adjust the check until it goes red — which would manufacture the appearance of a working guard.

**Ordering.** Task 4 comes last so the manual harness keeps its checks until the hermetic file has been proven end-to-end. If Task 3's red-proof came back negative and the design had to narrow, the checks would still be in their original home and nothing would need un-deleting.

**One thing deliberately not automated.** Nothing prevents a new table arriving over-granted; the guard only detects it afterwards. Ending table-creating migrations with a revoke stays a habit. Making it enforced would need an event trigger, which is a different project.
